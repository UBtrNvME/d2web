# 0010. Web performance is a standing constraint

Status: proposed (written 2 November 2026 at the user's request; not yet accepted).

Context: d2web paints a D2 board as native DOM ([ADR 0001](0001-native-web-foundation.md), [ADR 0009](0009-natural-web-forms.md)), so every cost the browser charges for DOM, style, layout, paint and compositing is ours. [ADR 0009](0009-natural-web-forms.md) made faithfulness a standing rule. Performance has so far been handled one complaint at a time, and the first real complaint ("the diagram is lagging when panning and zooming") found costs that were built in by ordinary-looking choices, not by anything exotic. The evidence, all from one machine and one scripted run each (use orders of magnitude, not digits):

- **A custom property on an ancestor restyles the whole board.** The demo's dot grid was driven by CSS variables set on `<main>`, which contains the board. On the "d2web in the D2 ecosystem" example (530 elements, 55 inline SVG fragments, 20 masked groups, about 243 KB of markup), a scripted pan of 80 pointer moves in headless Chromium with 6x CPU throttling spent 985 ms in style recalculation (80 recalculations) and ran 79 layouts, and the 95th-percentile frame was 33.3 ms. Moving the grid to a sibling layer, changing the zoom readout's text only when it changed, and applying input once per animation frame gave 96 ms, 0 layouts and 16.8 ms. Zoom style recalculation fell from 208 ms to 26 ms. Commit `2d1eed1`.
- **A text change forces layout.** The zoom readout rewrote its text on every frame, one source of those 79 layouts.
- **Masks cost nothing measurable in Chromium once the above was fixed, and are unmeasured elsewhere.** With the grid fixed, stripping all 20 label masks changed pan and zoom time by less than the run-to-run noise. Each connection currently carries its own inline image mask holding every label's hole (about 163 KB of style across 20 connections), so that cost grows with connections times labels. Safari does not resolve `mask: url(#id)` to an inline SVG mask from an HTML element, which is why masks became data-URI images (commit `209c34c`); Safari was not measured.
- **Compile cost is paid in full for render-only changes.** On the same example a theme switch took about 1.6 s end to end, 1.49 s of it inside D2 (parse, TALA layout, scene build), although a theme changes paint only. The protocol ([spec 0001](../specs/0001-compile-protocol.md)) compiles everything on every request. TALA layout time grows steeply with board size (see [layout limits](../layout-limits.md): 100 shapes took about 24 s on the measured machine; dagre and ELK stay in the low seconds at 1000).
- **Existing performance decisions** already in force: latest request wins and worker restart for stale compiles ([spec 0001](../specs/0001-compile-protocol.md) section 3.4), the explicit large-board engine switch ([ADR 0005](0005-layout-engine-policy.md)), fonts and scenes deduplicated and kept separate, a size budget for the package ([spec 0003](../specs/0003-packaging.md)), and Chromium as the only verified browser ([ADR 0007](0007-product-scope-v1.md)).
- Headless Chromium on a developer machine understates GPU raster and Safari or mobile cost. Every number above is a lower bound for a phone.

Decision: performance is a design constraint on every change to the painter, the protocol, the mount and the demo, in the same way faithfulness is. We reason about cost while designing, measure before and after any change that touches an interaction or compile path, and record the numbers. D2 still owns what is drawn: no optimisation may change a D2 value, drop a D2 effect or add a policy of ours silently. Where speed and fidelity conflict, the choice is an explicit consumer option (as with the layout engine in [ADR 0005](0005-layout-engine-policy.md)), never a default.

Strategies (the working rules):

1. **Keep the interaction path off the board.** Pan, zoom, hover and focus must not cause style recalculation or layout across the board. Camera movement is one `transform` on one wrapper. Per-frame state (a grid, a readout, a selection box) lives on sibling layers, never as custom properties or classes on an ancestor of the board. Do not write layout-forcing values (text, size, class) every frame; write them when they change. Do not read layout inside input handlers.
2. **One update per frame.** Wheel, pointer and resize input is coalesced and applied in one `requestAnimationFrame`. Work that can wait for idle does.
3. **Compile only when D2 would decide something different.** Typing, a new file or a new layout engine need a full compile. A change that only affects paint (theme, sketch, and anything D2 resolves after layout) should not pay for layout. This needs a protocol change (cache the laid-out diagram in the worker, rerun only scene build) and is a proposal, not yet specified or accepted. Until then, keep the debounce, latest-wins coalescing and the explicit engine switch, and do not add paint-only options that silently relayout.
4. **Budget the DOM.** A board is DOM nodes, inline SVG fragments, masks, clips and filters. Count them per example (the painter already reports stats) and treat growth as a cost. Prefer plain elements over SVG fragments where the HTML form is exact (already the painter's rule), avoid duplicating the same asset per object (the per-connection mask is the known case), and prefer a cheaper exact form (for example a `clip-path` path for rectangle holes) over an image mask only where it is provably equivalent to D2's mask.
5. **Swap, do not rebuild, when it matters.** The mount replaces the board's DOM on every update (parse of the full markup). That is acceptable at current sizes; the next step if it is not is keyed patching of unchanged subtrees, guarded by the identity and association rules ([spec 0004](../specs/0004-association.md)).
6. **Send less across the boundary.** Scenes and fonts stay deduplicated and fonts stay out of scenes; do not add fields that duplicate data the consumer can derive. Watch structured-clone and JSON size per board.
7. **Say what was measured.** A performance claim names the example, the browser, the throttle, the metric and the before and after. "Chromium only" is the stated limit until another browser is measured; Safari and mobile are labelled unverified, not assumed fine.

How we measure: scripted, repeatable interactions on a heavy example (the ecosystem example is the current heavy case), with the browser's own counters rather than wall-clock feel: style recalculation count and duration, layout count and duration, task duration, and 95th-percentile frame time, under 6x CPU throttling, headless Chromium, taken through the DevTools Protocol `Performance` domain. Counts are stable across machines and are what CI can assert; durations are for before-and-after comparison on one machine. `will-change: transform` on the camera wrapper showed no effect in this setup and can blur text at high zoom, so it is not used without evidence.

Review checklist for a change that touches the painter, mount, protocol or demo:
- Does anything set a custom property, class or text on an ancestor of the board per frame?
- Does an input handler read layout, or write a layout-forcing value every time?
- Is input applied once per frame?
- Does this make a paint-only change pay for layout, or send data the consumer can derive?
- Does it add DOM, masks, clips or filters per object? What is the growth per shape or connection?
- Was the interaction measured before and after, and are the numbers in the commit or PR?

Alternatives: optimise only when someone reports lag (rejected: this one was found late and was built into the architecture by ordinary choices, so it would have kept recurring; the per-event restyle came from a convenient place to put a CSS variable); render the board to a canvas or WebGL for speed (rejected by [ADR 0001](0001-native-web-foundation.md) and [ADR 0009](0009-natural-web-forms.md): native DOM is the product, with accessibility, selection and consumer-replaceable content); hard performance budgets with CI failure on durations (not now: millisecond thresholds are machine-specific and flaky; counts can be asserted, see Consequences); virtualise or cull off-screen objects (not now, no evidence it is needed at the sizes D2 renders, but listed as an open option for very large boards).

Consequences:
- Changes that touch interaction or compile paths carry a measurement. This costs a few minutes and a repeatable script, not a framework.
- Open and not decided here: a worker-side cache of the laid-out diagram (needs a spec 0001 change and your acceptance); sharing the label mask across connections or replacing it with an exact clip where D2's mask is only rectangular holes; keyed DOM patching on update; measuring Safari and a real phone; a counts-based performance test (zero layouts and no more than a fixed number of style recalculations during a scripted pan) that could join `check:browser`. The measurement script used for the numbers above is not yet in the repository; adding it is the first follow-up.
- What would reverse this: evidence that the checks cost more than they save, or a decision to treat a different renderer as the product.

Evidence: [layout limits](../layout-limits.md), [spec 0001](../specs/0001-compile-protocol.md), [browser support](../browser-support.md), commits `209c34c` (masks as data-URI images) and `2d1eed1` (pan and zoom cost). Numbers in Context are from 2 November 2026 on one Linux machine, headless Chromium, 6x CPU throttle, one run each.
