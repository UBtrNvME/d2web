## What this says about readiness

- Accepted: native HTML/JS/CSS/SVG foundation, reuse of Go/WASM for compile/layout/theme semantics, combined join boundary (Checkpoint A), HTML-first painter with SVG fallback inside a shadow root and per-mount ID prefixes (Checkpoint B, Option 1; research scope), oracle fixes carried as an opt-in patch set.
- Proposed with evidence, not yet accepted: worker-hosted persistent wasm sizing loop with latest-wins scheduling; copy-on-write edit wrapper; named per-object accessibility groups from scene IDs.
- Not decided: font delivery (row 3), layout engine policy for large boards (TALA is not interactive above about 50 nodes; dagre/ELK are, with different layouts), renderer coverage for images, animation, themes and non-root boards (rows 4, 6), consumer content for containers and edge labels (D2 cannot be asked for their size), and the public contracts in every row.
- Highest remaining risk: layout cost and engine choice for big boards, then font bytes and fallback, then renderer coverage beyond plain boards.

Accepted decisions are recorded in [docs/adr](adr/README.md); no further ADR is ready.

## Checkpoint A outcome (31 October 2026)

User reviewed R1/R2 evidence: combined boundary is the only one carried forward; HTML-first with CSS masks is the painter R3 and R6 probe; fidelity bar is 5% raster difference plus recorded failures; font policy is explicit consumer-approved assets, no fallback fetching. These narrow the research, they do not select the stack.

## Checkpoint B outcome (31 October 2026)

User chose Option 1: combined boundary, HTML-first paint with SVG fallback in a shadow root with an `all:initial` wrapper and per-mount ID prefixes. Research choice, not accepted architecture; no ADR is ready. Next gaps: R4 edits in Chromium, R6 measured-card recompile loop with a real shadcn consumer.

## Checkpoint C (R5 draft, awaiting user review)

R3, R4 and R6 gaps that could be probed locally are closed or recorded in [todo](../tasks/todo.md). What needs the user: (1) whether the shadow-root host plus worker-hosted sizing loop becomes the proposed runtime shape, (2) layout engine policy for large boards, (3) whether container/edge-label sizing limits are acceptable or need an upstream request, (4) font delivery, (5) which contracts to draft as ADRs. The user answered and accepted ADRs 0003-0006 (see below).

### Checkpoint C answers (31 October 2026)

Runtime shape: user agrees with the direction, asked for a plain explanation of the sizing loop (not yet accepted). Layout: TALA preferred; ELK/dagre acceptable when TALA is too slow. Container/edge-label limits: agreed; user asked whether consumers can supply their own edge labels (probe: a same-text label with `style.font-color: transparent` reserves identical space; whitespace-only labels crash TALA). Fonts: agreed; bundle common fonts and load others on demand from consumer-approved CDNs. ADRs 0003-0006 were then accepted by the user, with the edge-label and font notes folded in.
