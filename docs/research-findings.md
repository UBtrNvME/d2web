## Framework comparison: documentary findings

These official docs are moving references checked during this investigation; they do not pin installed experimental versions. A framework's documented capability is not evidence of compatibility with D2.

| Question | React Flow | JointJS |
| --- | --- | --- |
| Custom presentation | Consumer React nodes receive identity/data inside interactive wrappers: [custom nodes](https://reactflow.dev/learn/customization/custom-nodes) | Current first-party React binding supports custom elements, style-neutral HTMLHost and styled HTMLBox: [elements](https://docs.jointjs.com/react/features/elements/) |
| Native route preservation | BaseEdge accepts SVG path data; using React Flow's route helpers is not compulsory: [BaseEdge](https://reactflow.dev/api-reference/components/base-edge) | Links have endpoints/routers/connectors; custom connectors can supply path data. Current renderLink is experimental: [links](https://docs.jointjs.com/react/features/links/), [connectors](https://docs.jointjs.com/api/connectors/) |
| Dimensions | DOM measurement and handles require coordination with supplied dimensions: [node](https://reactflow.dev/api-reference/types/node), [handles](https://reactflow.dev/learn/customization/handles) | HTML content normally influences model size; explicit size/useModelGeometry can fix the footprint: [custom elements](https://docs.jointjs.com/react/getting-started/custom-elements/) |
| Nesting/ordering | Parent-relative coordinates and ordering rules require adaptation; model parenthood is not nested DOM: [subflows](https://reactflow.dev/learn/layouting/sub-flows) | Embedding affects child positions and embedded-link vertices: [grouping](https://docs.jointjs.com/learn/features/containers-and-grouping/) |
| State and interaction | Controlled nodes/edges are possible; built-in keyboard/focus behavior can affect viewport: [API](https://reactflow.dev/api-reference/react-flow), [accessibility](https://reactflow.dev/learn/advanced-use/accessibility) | Controlled cells are possible; default connection validation/interaction policy needs review: [controlled mode](https://docs.jointjs.com/react/data-management/controlled-mode/), [links](https://docs.jointjs.com/react/features/links/) |
| Accessibility | Built-in facilities save work but defaults still need an explicit consumer policy | Official custom-element docs leave roles, focus order and keyboard behavior to the application |
| Adoption cost | React dependency and an additional diagram state/DOM model; adapting it may save interaction work | SVG-oriented model and React integration; experimental link customization and additional graph policy need testing |

Source licensing/dependency references: [React Flow manifest](https://github.com/xyflow/xyflow/blob/main/packages/react/package.json), [system manifest](https://github.com/xyflow/xyflow/blob/main/packages/system/package.json), [JointJS React manifest](https://github.com/clientIO/joint/blob/master/packages/joint-react/package.json), [JointJS licensing](https://www.jointjs.com/license). The documentary comparison identifies MIT for React Flow and MPL-2.0 for JointJS core/React; paid JointJS+ facilities must not be counted as core. Recheck exact installed versions and terms before adoption.

[Cytoscape.js](https://js.cytoscape.org/) offers another useful comparison: graph-focused, canvas-based presentation with preset geometry. Inference: graph analysis may benefit, but arbitrary accessible/selectable HTML and D2 painting would still need another presentation boundary. It is not rejected through a local experiment and is not a selected dependency.

[shadcn's open-code/composition model](https://ui.shadcn.com/docs) supports investigating consumer-owned presentation rather than a mandatory core design system. Actual shadcn components, portals, themes and changed-size layout remain unverified here.

All three options remain under consideration: adopt a diagram framework, build a bounded adapter over one, or implement D2 presentation while borrowing platform patterns. Frameworks can save accessibility, event and viewport work; custom presentation avoids a competing graph model but leaves that engineering to d2web/consumers. Neither tradeoff wins from documentation alone.

Observed across three workspaces/seven boards:

- Repeated native compilations and Node/WASM executions produce equal **reported projections**: board paths, selected semantic/property/source fields, target IDs and flat scene ID/type records. This does not compare full scene geometry, paints, fonts or assets.

### Join stress probe (combined boundary)

Reproduce with `mise run test:research:join` (inputs in [research/join](../examples/research/join/), reuses research/identity.go; native equals Node/WASM; report in ignored artifacts/research-join/findings.json). Named cases only.

- **Holds:** every semantic object/edge ID has a scene node with the same ID in all five cases, including sql_table, class, markdown and nested containers. Generated scene nodes are `<ownerID>:<suffix>` (`t:table-row:0:name`, `k:class-method:0:type`, `m:markdown:primitive:0`, `(t -> k)[0]:path`); the only ownerless ones are `root` and `root:background`. So an owner-prefix rule maps scene nodes to objects in these cases.
- **Breaks as a stable key:** rename changes the ID (and the IDs of every touching edge), and ID alone cannot tell rename from delete+create. Parallel edges are index-based: deleting `(a -> b)[1]` makes the old `[1]` ID name the former `[2]` edge, so a survivor changes ID and an old ID silently names a different edge. Stale results also repoint: IDs reused across revisions resolve to different source ranges (shifted ranges here, but a retargeted ID would look the same).
- **Implication for the combined contract:** the join key must be (revision, board path, ID), identity across edits needs source ranges or a caller-supplied mapping, and parallel-edge identity cannot rely on index. Prefix-parsing generated IDs is an observed convention, not a documented guarantee; the association layer should carry the scene-node list explicitly rather than have consumers parse IDs.
- **Not covered:** a real late-result/cancellation transport, edit operations driving the rename, nested-board joins beyond the earlier probe, and non-TALA engines.

### R2 rich content: what the native scene carries (second pass)

Reproduce with `mise run test:research:rich` ([inputs](../examples/research/rich/), [probe](../research/rich.go); native equals Node/WASM; report in ignored artifacts/research-rich/). The scene is dumped with TALA seed 1; no browser rendering or pixel comparison was done, so this is about *data available to a web renderer*, not fidelity.

- **Markdown** becomes indexed primitives `m:markdown:primitive:N`: TextRuns split per style (regular, bold, italic, semibold heading at 32px, SourceCodePro at 13.6px for inline code) plus plain Rects for rules and bullets. No element carries heading/list/emphasis semantics, and the link text is an ordinary run with one separate scene link region. An HTML renderer would have to reconstruct structure or render the runs as positioned spans; semantic HTML (h1/ul/strong/a) is not recoverable from the scene alone and would need the source/graph.
- **Code** becomes `c:code-line:L:token:T` TextRuns in SourceCodePro on a background Rect. Whitespace tokens are omitted (line 0 has tokens 0,2,3,4,6), so indentation is positional only. Text selection or copy would need the runs reassembled per line.
- **LaTeX** is rejected by the scene builder (`unsupported label language latex without configured SVG import limits`) unless the caller supplies explicit SVG-import limits and budget (research values used here, not recommendations). With them it is a single `Image` node `l:label:0` backed by a vector asset: no TextRun, so not selectable or searchable. This is consistent with the explicit-resources design but means a web port must choose those limits.
- **Unicode** (CJK, emoji, Arabic): every run uses SourceSansPro bold; the scene has no fallback font because no fallback resolver is configured. Glyph counts equal rune counts (7 and 19), so no joining/ligature reduction is visible for Arabic. Zero glyph IDs of 0 were counted, which does not tell us what is drawn; whether these glyphs render correctly is **not verified** and needs a browser/visual check with a configured fallback resolver.
- **Multiline**: explicit `\n` makes one run per line (`a:label:0`, `a:label:1`). `width: 120` does not wrap the 253-wide label, so the text overflows the box (native layout behaviour; the scene faithfully keeps it).
- **Implication for the combined boundary:** for rich content the scene is fine as faithful paint but loses structure, so the association layer needs per-object content roles (markdown/code/latex) and the owner prefix so a consumer can opt into semantic HTML. Latex and fallback fonts need explicit resource configuration in any public runtime API.
- **Not covered (data side):** Unicode rendering, the earlier 1.64px subset-font discrepancy for these fonts, sql_table/class text selection, shaping correctness for complex scripts, markdown inside containers/edges, and tooltips.

**Browser pass (markdown and code only).** `research/rich-browser.mjs` exports each case's text runs (with accumulated node transforms), the scene's font bytes and D2's native SVG; [research/browser/rich.spec.mjs](../research/browser/rich.spec.mjs) repaints only the TextRuns as SVG `<text>` using each scene font via FontFace and compares every run's rect with the same text in the native SVG (DOM Range). Chromium 156: all 12 markdown and 12 code runs matched; max |Δx| 0.0004px (markdown) and 0.16px (code), max |Δwidth| 0.17px and 0, vertical offset 0. Native markdown is plain HTML-in-SVG text nodes, not paths. The spec's 0.5px ceilings record this observation; they are not parity thresholds. So for these Latin cases a scene-driven renderer reproduces D2's text placement without fitting or compensation, and the 1.64px label gap seen earlier did not recur (no ligature sequences like "ffi" here; the cause of the earlier gap is still not established).
Not painted or compared: rule/bullet/code-background rects, the link region, selection/copy behaviour, pixel comparison, the latex vector, or other browsers. The screenshot (artifacts/research-rich/markdown.png) is for visual inspection only; it showed the scene repaint lacks bullets and the heading rule because rects were not drawn.

**Unicode and fallback fonts (CJK, emoji, Arabic).** Without a resolver every glyph stays on Source Sans Pro bold. With the CLI-style chain (host system fonts, then bundled Noto Color Emoji; research limits) the native scene resolved three extra font assets on this Mac: a host CJK face (23.5 MB, serving all 7 glyphs of the Japanese label), a 0.75 MB Arabic face (7 glyphs) and the 5.0 MB colour-emoji face (1 glyph); Latin and the accented é stay on the primary font (11 glyphs). Per-glyph asset overrides are retained in the scene (`Glyph.Asset`). **The Node/WASM build resolved zero fallback fonts** (no host filesystem), so native and WASM scenes differ for non-Latin text; a web runtime must have the consumer supply fallback fonts, and those bytes are large (nothing is subset).
Browser repaint (Chromium 156) of those two runs with a CSS font stack of the primary plus scene fallbacks, loaded from the exported font files: CJK, joined Arabic and colour emoji all render. The scene's own glyph-advance sum matches the browser-measured run width (112 vs 112; 131.28 vs 131.27), while D2's native SVG text, which relies on Chromium's own fallback choice, is 0.97 and 1.22px wider and lighter, so the native SVG is not a stable reference for non-Latin text. Unicode comparison is recorded only (host-font dependent, so no ceilings are asserted). Not verified: what the primary-font-only scene paints for CJK (glyph IDs were all non-zero, so tofu is not confirmed), bidi/RTL ordering for longer text, other browsers or operating systems, subsetting, and fallbacks for bold/italic styles.

**Imports, class and glob edges (second pass).** Inputs: [imports](../examples/research/join/imports/), `imports-shift` and `imports-delete` (same folder); the identity probe now also reports edge style values with the declaration that owns them. Native equals Node/WASM for the base workspace.
- **Imported edges keep their file.** `imp: @shared` yields `imp.(a -> b)[0]`/`[1]` with references in shared.d2, and a local `imp.a -> imp.b` in main.d2 continues the same index (`[2]`). Scene nodes exist for all of them (`imp.(a -> b)[2]:path`, `:label:0`, `:dst-arrowhead`; an extra `:geometry` node appears for edges in this case).
- **Cross-file renumbering:** inserting one edge at the top of shared.d2 turns the local edge from `[2]` into `[3]` without touching main.d2. An ID from an earlier revision therefore can name a different edge even when the consumer's own file did not change; the (revision, board, ID) key is still not enough to carry identity across edits, and a source-range mapping would need to span all imported files.
- **Property ownership is separate from references.** A class-derived `stroke: red` points at the class declaration (main.d2 line 1), which is not in the edge's references. A glob `(* -> *)[*].style.opacity` is one declaration owning opacity for several edges, and also appears in each edge's references. An index-targeted override `(x -> y)[1].style.stroke-width: 5` sits in that edge's references. The association layer must expose per-property sources and cannot derive them from the reference list.
- **Counterexample, authored index references:** removing the first `x -> y` edge while keeping `(x -> y)[1].style.stroke-width: 5` fails compilation: `main.d2:7:2: indexed edge does not exist`. Edge deletion in an editor must also rewrite or remove authored index references, and a probe-compiled "after" document is not guaranteed to exist.
- **Not covered:** nested boards with imported edges, edge renames via imports (`...@file` spreads), imported classes, globs crossing import boundaries, and any edit operation performing these changes natively.

### Corpus scene census (what a browser renderer must paint)

`mise run test:research:census` ([probe](../research/census.go), [runner](../research/census.mjs); output in `artifacts/research-census/`) builds a native TALA scene for every board of all 147 corpus runs (31 Oct 2026, ~4s). Offline: local images resolve from the workspace, remote ones are unavailable and the builder substitutes its missing-image placeholder (so the 26 images are not remote-image evidence). Native only, no browser painting and no parity; it measures demand.
- **Every board builds:** 173 boards (147 runs, 5 with layers/scenarios/steps), 0 refused. One probe correction: `Build` rejects a diagram that carries nested boards, so each board is built alone. A consumer must build per board and join boards itself.
- **Demand by runs using it:** TextRun 144, Rect 147, Path 119, Image 26, Ellipse 20; solid fill 147, radial gradient 2, linear gradient 1, pattern 2; drop shadow 6; mask 55, clip 25, blend 3, animation 6, transform 106, opacity 43; font assets 144, vector assets 26, raster 1.
- **Existing adapter coverage:** `research/geometry/geometry-scene.ts` rejects assets, links, filters, animations and unsupported viewport, and has no text primitive. Only 2 of 147 runs use no text, image, mask, clip, blend, animation or filter, so the parity-capable subset is about 1% of the corpus. Text (144 runs) and masks (55) are the two largest missing renderer capabilities; gradients, patterns, shadows, blend and animation are rare (1 to 6 runs each) but each needs its own case.
- **Consequence:** the browser renderer's real scope is text runs plus masks and clips, then images/vector assets. A parity run over the corpus needs a scene serialization (the bridge) beyond the 157-line adapter. Not done: serialization, painting, native/browser image comparison.

### Corpus text repaint (text painter pass)

`mise run test:research:census` also repaints every root-board TextRun of all 147 runs as SVG `<text>` in Chromium with the scene's own font bytes ([spec](../research/browser/census.spec.mjs), per-run data in `artifacts/research-census/browser.json`), and compares each run's box with the same text inside D2's native SVG. 5,947 runs: 54 empty, 20 not found in the native SVG (fulcro_rad, spyre_encoder, unicode: long or markdown-like text), 0 carry a non-translation transform, 5,873 compared (all inside SVG text, none in `foreignObject`). One Chromium on this machine; Latin and bundled fonts only, no fallback resolver. Measurements, not thresholds.
- **Against native SVG:** 4,589 of 5,873 (78%) agree within 0.5px on left, width and top; 5,088 within 1px; 5,626 (96%) within 2px. Widest width gap 8.5px (a 20-character bold label).
- **Against D2's own advances:** the repainted scene width is within 0.5px of the sum of the scene's glyph advances for 5,712 of 5,873 (97%); the native SVG is within 0.5px for only 4,598 (78%). So the scene repaint reproduces what layout measured, and the disagreement is mostly the native SVG's embedded subset fonts rendering wider (about 1 to 3px per label, e.g. `cccccccccccccccccccc` bold: native +8.5px). This matches the earlier unexplained 1.64px subset-font gap. Cause not isolated (kerning, hinting or the woff subset); not checked by weight.
- **Implication:** pixel parity against native SVG cannot be the text acceptance test. Layout-consistent parity (scene paint equals measured advances) is met in 97% of runs; the 3% remainder is not yet examined. Native SVG is itself inconsistent with D2's layout in this browser.
- **Unexplained:** a few comparisons show 100 to 2,500px offsets; the ones inspected are matching ambiguity (repeated short text such as `x` matched to a different node), but not all 76 outliers were traced. Empty text runs must be skipped.
- **Not done:** non-Latin and fallback fonts across the corpus, markdown/code through foreignObject, bold/italic synthesis, rotated or scaled text, text decoration, and painting of the other primitives, so no whole-image comparison.

### Corpus whole-image paint (all primitives)

A research painter ([packages/d2web/src/paint.js](../packages/d2web/src/paint.js), about 150 lines) turns the tagged scene dump into SVG markup covering every kind the corpus uses: rect, ellipse, path (move/line/quad/cubic/arc/close), text, raster and vector images, solid/linear/radial/pattern paint, strokes with caps/joins/dashes, clips, alpha/luminance masks, blur/drop-shadow filters, blend modes and transforms; animations are not painted. [research/browser/paint.spec.mjs](../research/browser/paint.spec.mjs) paints each root board, rasterizes it in Chromium and compares with D2's native SVG raster (pixel counted different when any channel differs by more than 25, composited on white). Results are per case in `artifacts/research-census/paint.json`; not tuned.
- **The painter handles every primitive and paint kind in all 147 runs** (no error). Most of the work was serialization, not painting.
- **Agreement:** of 145 comparable cases, 26 differ in at most 0.1% of pixels, 100 in at most 1%, 139 in at most 5%. Excluding the 26 cases with images and the 6 animated ones, all 114 are within 5% (25 / 90 / 114 within 0.1% / 1% / 5%); the worst is 3.7% (`width-smaller-than-label`), then icons_on_top 3.5%, markdown 2.5%, unicode 2.4%. Not traced further.
- **The four worst first-run cases were not renderer gaps** (traced with native/scene/diff images):
  - `sketch-cross-arrowhead` (11%) and `sketch-mode-circle-arrowhead` (6%): the probe never set the scene build option `Sketch` (it is a build option, with a budget, taken from the compile's render options). With it set, both leave the worst list. Sketch is built into the scene by D2's own Go port of rough.js (`d2sketch`, `rough-go`) as ordinary Path nodes plus the hand-drawn font, so the browser needs no sketch library; it paints the paths it is given.
  - `tpmjs_architecture` (23%) and `nesting_power` (6%): my painter, not D2. Chromium stopped painting anything below about 2,500px in 7,430px and 2,000px in 3,135px tall boards when masks used a document-sized `userSpaceOnUse` region (removing masks restored it). Default object-bounding-box mask units fix it. Large masked boards are a real browser risk for a DOM painter: a rendering limit, not a scene limit. Zero-height strokes under bounding-box masks were not specifically examined; the 114-case result suggests no visible effect here.
- **Images are not comparable this way:** native SVG links remote files (network-dependent) or local paths that cannot load, while the scene embeds assets or the builder's missing-image placeholder (this census builds offline). That is a real contract difference: the scene is self-contained; native SVG is not.
- **Links are not painted by the scene.** `boards__all` and `boards__nested` differ in size (native 72x85+ vs scene 55x68): native draws a link icon, the scene carries a LinkRegion instead. A consumer must render link/tooltip affordances itself.
- **Probe bugs found on the way:** the first run omitted theme overrides (`theme-overrides` differed in 99.6% of pixels) and the sketch flag (see above). Both are compile-resolved render options. Any bridge must carry them from the compile, not defaults.
- **Not done:** animation painting, dark theme, sketch/pattern correctness analysis, more than one Chromium, non-root boards, events/DOM association, performance (full run is about one minute for 147 boards), and the scene dump is a reflection of Go types, not a designed schema.

### HTML-first presentation probe

The same painter has an HTML mode (`paintScene(scene, { html: true })`; [spec](../research/browser/html.spec.mjs), per case in `artifacts/research-census/html.json`). Real elements where an HTML equivalent is exact enough: rect and ellipse as bordered `div`s (solid fill, solid opaque undashed stroke), text as positioned `div`s with the scene's own font, raster images as `<img>`, link regions as `<a href title>` overlays. Everything else is a nested `<svg>`, with every fallback reason counted. Any node with a mask, clip, filter, blend or animation paints its whole subtree as SVG (a deliberately simple rule). Same 147 boards, same pixel comparison with native SVG.
- **Accuracy:** all 114 cases without images or animation are within 5% of native pixels (all-SVG painter: 114); 85 are within 1% (all-SVG: 90). Worst: geometry 3.9% (all-SVG 0.01%), width-smaller-than-label 3.9%, icons_on_top 3.6%, jupyter_aws_eks 2.5% (all-SVG 0.4%).
- **Cause of the HTML-only deltas:** layout snaps box edges to whole pixels. `geometry` has a 3px border at left -1.5px and a 59px width, which SVG anti-aliases but HTML snaps. Consistent with the coordinates; not isolated beyond that. Odd stroke widths and half-pixel origins are common in D2 scenes, so exact edge parity is a property SVG gives and HTML does not.
- **HTML share is only 36% of primitives** (8,834 HTML: 5,467 text, 3,327 rects, 40 ellipses; 15,881 SVG). The cause is the subtree rule, not the primitives: 14,380 of the 15,881 SVG primitives sit under an effect node. Of 843 effect nodes: mask 627, clip 144, blend 26, filter 24, animation 24. D2 puts masks (label cut-outs) on groups that contain many shapes, so one mask turns a large subtree to SVG (chess: 56 of 63 rects). Outside effects, the remaining SVG fallbacks are paths 1,184 (all connections, arrowheads and non-rectangular shapes), vector images 209, dashed or translucent strokes 101, gradient/pattern fills 5, text with stroke 2. Paths are inherently SVG.
- **Practical reading:** text, labels, rectangular boxes, images and links are DOM-ready. Connections and shaped geometry stay SVG. Reaching a high HTML share needs masks and clips to be applied to smaller groups or expressed per element; that is a scene-construction or painter-restructuring question, not yet tested.
- **Text needs baseline calibration.** HTML places text by line box, not baseline. The probe measures an empty inline-block in each element after fonts load and shifts the element so the baseline lands on the scene's y (a layout read per text run; 5,467 runs rendered within the text tolerance above). A product would need font ascent metrics from the scene or the same measurement; neither is in the scene today.
- **Selection and accessibility (4 boards, Chromium):** selecting all text copies every label in both variants, but HTML copied adjacent labels run together (`Hans NiemanndefendantsMagnus Carlsen`) because absolutely positioned elements carry no whitespace. Fixed: each HTML text label now ends in a newline inside its `white-space:pre` element, and the copy reads `Hans Niemann defendants Magnus Carlsen …` like the SVG variant; raster ratios were unchanged (85 cases within 1%, 114 within 5%). Reading order is still paint order, not semantic order. The accessibility snapshot shows each HTML label as plain text and the SVG variant as one `img` whose name concatenates all labels. Neither has structure (no roles, no object-level grouping). Links become real `link` nodes in the HTML variant (markdown case) and are absent in the SVG variant. Not tested: screen readers, keyboard focus, find-in-page, tooltips, RTL.
- **Bug found while painting:** CSS `matrix()` needs commas; the space-separated form that SVG attributes accept is silently ignored in `style`, which put arrowheads at the origin (geometry was 13.7% then).
- **Accessibility grouping (`test:research:a11y`, 4 boards, Chromium):** every direct child of the scene root that is not a `root:*` helper is a D2 object or connection. Painting it as `role=group tabindex=0 aria-label=<its label runs, else its ID>` is derivable from scene data alone and changes no pixels (screenshots byte-identical on all four boards). Tab visits exactly those groups in paint order (13, 3, 211, 21 stops). The accessibility tree shows named groups ("Hans Niemann", "Owns majority"). Gaps seen: containers are flat siblings of their children in the scene, so no group nesting; objects without label runs fall back to the raw ID such as `financial.monthly` (0 of 13 on chess; 10 of 21 on md-tables, where the text lives in table content rather than `:label:` runs, so they are named by ID and their table text is an unnamed `img`); SVG-fallback pieces and the background appear as nameless `img`; markdown table content reads as one run-together `img` name. Names come from the paint, so an opacity-zero label would have no name (see the identity finding): the association layer must supply names for those. Screen readers, find-in-page, tooltips and arrow-key policy remain untested. A research choice, not a proposed API.
- **Not done:** CSS masks on HTML groups, markdown/code as DOM structure (still scene runs), per-object grouping for accessibility, consumer replacement of node content, events/hit-testing, and any other browser.

### CSS masks and clips on HTML groups

With `D2_CSS_MASKS=1` the HTML painter keeps masked and clipped groups as `div`s and applies `mask: url(#id)` / `clip-path: url(#id)` to them; only filter, blend and animation subtrees stay SVG. A masked group is given the document extent at the local origin because CSS mask and clip references resolve against the element's border box (a zero-size group masks everything away). Same 147 boards and comparison; results in `artifacts/research-census/html-summary-css-masks.json`.
- **HTML share doubles:** 72% of primitives are real HTML (10,475 of 14,634), up from 36%. 627 masked and 143 clipped groups stay DOM; remaining SVG is 1,308 paths in effect subtrees plus the 1,184 paths and 209 vector images that are SVG anyway; only 92 effect subtrees (filter 24, blend 26, animation 43) are still SVG.
- **Accuracy holds:** 113 of 114 plain boards within 5% of native pixels (88 within 1%; was 114 and 85).
- **One regression, a browser limit:** `nesting_power` (10,052 by 3,135px) rises to 5.8% (all-SVG painter: 0.1%). The differing pixels are all below about y 2,000 in the columns of the large masked containers, the same region that went blank with SVG masks before default mask units were used. Chromium here does not paint mask-covered content past roughly 2,000 to 2,500px vertically on very large masked areas; masking is therefore unsafe on huge groups. Candidate fix, not tested: size each masked group to its subtree bounds instead of the document extent.
- **Costs:** every masked group needs a box, so masks and clips become layout-visible; coordinates inside depend on the group being at the local origin. A consumer replacing node content inside a masked group inherits the mask.
- **Not done:** subtree-sized mask boxes, filters/blend as CSS, other browsers, performance of 600+ masks on one page, and hit-testing under masks.

#### Subtree-sized mask boxes

`D2_CSS_MASKS=subtree` (now what `test:research:census` runs) sizes each masked or clipped group to the conservative painted bounds of its own subtree (stroke widths doubled, arcs and text over-estimated) instead of the document extent. Mask and clip definitions are shifted by the box origin and the transform origin stays at the local origin (`artifacts/research-census/html-summary-css-masks-subtree.json`).
- **The large-board regression is gone:** `nesting_power` leaves the worst list; all 114 plain boards are within 5% of native pixels and 89 within 1% (document-extent boxes: 113 and 88). The HTML share is unchanged at 72% (10,475 of 14,634 primitives). This supports the reading that the Chromium problem was the size of the mask raster, not masks on HTML groups.
- **Costs:** the painter now needs subtree bounds. Text bounds here are an over-estimate from string length and font size because the scene has no ink bounds for the runs I read; a product would use the scene's `Ink` or measured advances. Group boxes also become layout-visible and overlap.
- **Not verified:** that mask raster size is the actual Chromium limit (not isolated), larger boards than 10,052px, other browsers, hit-testing under masks.

### Copy-on-write edit wrapper (R4)

Reproduce with `mise run test:research:transaction`. The [probe](../research/transaction.go) edits a freshly compiled disposable graph, formats the entry file, recompiles that text, and returns text only if it compiles. The same edit is also applied in place to a second graph as the contrast. Native and Node/WASM results are equal. Two workspaces: `examples/research/join/imports` (imported file, authored `(x -> y)[1]` index reference, glob `(* -> *)[*]`) and a glob-free three-edge file.

- **Rejected edits publish nothing:** setting opacity 2 fails with the compiler's message and returns no text; the in-place contrast leaves `x.style.opacity: 2` in the live AST. The source text of record is untouched, so atomicity comes from keeping text authoritative and discarding the graph, not from the oracle.
- **Native panic:** deleting `(x -> y)[0]` crashes `d2oracle.Delete` (nil dereference at `d2oracle/edit.go:1031`, `*ref.MapKey.EdgeIndex.Int--`) because the glob reference `[*]` has no integer. In WASM this would end the runtime unless recovered; the probe recovers and reports it. The in-place contrast leaves a half-edited AST (edge removed, later index not renumbered). Minimal reproduction: `x -> y` twice plus `(* -> *)[*].style.opacity: 0.8`, delete `(x -> y)[0]` (the last edge deletes fine). A one-line guard (`&& ref.MapKey.EdgeIndex.Int != nil`, [patch](upstream/d2oracle-delete-glob-index.patch)) removes the panic, leaves `x -> y` and the glob line, and the pinned `d2oracle` unit tests pass with it. The patch is not applied to `imports/d2`, which `check` requires to be the pristine v0.9.0 commit; the wrapper's panic recovery is the d2web-side guard.
- **Authored index references renumber:** deleting the middle of three parallel edges changes `(a -> b)[2]` to `[1]`; renaming `x` to `z` rewrites `(x -> y)[1]` to `(z -> y)[1]`. The oracle's delta maps cover compiled edge keys.
- **Imported edge delete:** produces a local `imp.(a -> b)[0]: null` override and leaves `shared.d2` unwritten, but the delta map still reports `imp.(a -> b)[1]` shifting to `[0]`. Deltas describe compiled IDs after the edit, not edits to the imported file.
- **Deleting a missing key** succeeds with unchanged text (no error). **Formatting:** deleting an edge leaves a blank line.

Limits: one entry file per edit (the oracle edits the entry AST, so no imported-file rewrite was tested); no undo, stale requests, UTF-16 range check after editing, or Chromium execution; the panic is shown for one glob shape only.

The wrapper rejects both and publishes nothing. All 17 outcomes, including the recovered nil-pointer panic, are identical in native, Node/WASM and Chromium WASM (the probe is a CLI main run through `wasm_exec.js`, one instance per request); this is diagnostic execution, not a proposed browser API. Not done: undo and stale requests, UTF-16 ranges after editing, the upstream report.

### R6, native side: size handshake by recompile

Reproduce with `mise run test:research:handshake` ([test](../research/handshake.test.mjs), input `examples/research/handshake/main.d2`: four label-free nodes, four edges, TALA, right direction). A consumer card's measured size is fed back as `b.width` and `b.height`, the board is recompiled natively, and the scene is checked. Node-side Go census probe, not WASM; sizes come from fixed numbers, not a measured DOM card.

- **Sizes are honoured exactly:** 40×30, 200×90, 320×160 and 60×300 all produce a box of the requested size (default is 100×100), with no overlapping nodes, 2 to 3 neighbours relaid out, 3 to 4 of the 4 routes changed, and edge endpoints within 4px of a node box (arrowhead allowance).
- **Layout is global:** a size change moves other nodes and the board extent (267×372 up to 652×297 across the four cases), so a consumer that resizes one card must accept a new layout for the whole board, not a local reflow.
- **Edge cases:** a fixed size wins over a wider label (40×30 box, label overflows). A circle with unequal width and height, zero width and a negative height are rejected at compile with specific messages. 5000×5000 is accepted (limit is 1e9).
- **What this adds to the Card case:** the existing consumer probe showed one resized rectangle; this shows several sizes and aspect ratios, the rejection modes, and that the full-layout cost is the price of the handshake.
- **Inheritance reset (`test:research:lifecycle`, two board pairs, Chromium):** shadow isolation alone left 8.2% and 1.2% raster difference on the gradient pair under hostile page CSS (inherited text properties on the host). A `:host{all:initial}` rule did not help because the page's `*` rule on the host element beats it. Wrapping the paint in `<div style="all:initial;display:block;visibility:inherit">` inside the shadow root gave 0 differing pixels in both hostile and clean runs (re-checked after adding the painter's text baseline calibration to both the baseline and every mount; before that the comparison used uncalibrated label positions). Side effect found on the way: plain `all:initial` also resets `visibility`, so a consumer hiding the host stopped working (59.8% difference) until `visibility:inherit` was restored; other inherited properties a consumer relies on (direction, cursor, pointer-events) are likewise reset and not yet tested. Research choice, not an API.

Limits: no DOM measurement or ResizeObserver loop; no labels, containers, grids, sequence diagrams or non-TALA engines; WASM execution and a browser-side sizing API are not tested; latency per recompile is not measured; the edit-to-source path (writing `width`/`height` as an operation) uses plain text appends here.

## Images and icons: what native D2 does (2 November 2026)

Evidence for [ADR 0011](adr/0011-images-like-native-d2.md). Native `d2` built from the pinned `imports/d2` checkout (commit d5a5174; its `--version` prints `v0.8.1-HEAD`), `--layout dagre` (no TALA plugin needed to observe image handling), Linux, network available. One run per cell; every cell is the exit code and what ended up in the output. The remote cases fetch `https://icons.terrastruct.com/…`, so this is a manual probe: it needs network and is not part of `check`.

```
D2=imports/d2 && (cd $D2 && go build -o /tmp/d2 .)      # pinned checkout, repo Go cache
x: Go {shape: image; icon: https://icons.terrastruct.com/dev%2Fgo.svg}      # remote
x: Go {shape: image; icon: ./go.svg}                                        # local file
x: Go {shape: image; icon: "data:image/svg+xml;base64,…"}                   # data URI
x: Gone {shape: image; icon: https://icons.terrastruct.com/dev%2Fdoes-not-exist.svg}   # 403
x: Nowhere {shape: image; icon: https://no-such-host.invalid/x.svg}         # unresolvable host
x: Chrome {shape: image; icon: https://icons.terrastruct.com/dev%2Fchrome.svg}  # gradients outside <defs>
d2 --layout dagre case.d2 out.svg | out.svg with --bundle=false | out.png
```

| Case | SVG, default (`--bundle` is **true** by default) | SVG, `--bundle=false` | PNG (the scene and raster path) |
| --- | --- | --- | --- |
| remote | fetched at compile time, inlined as a `data:` URI | link kept (`href="https://…"`) | fetched, painted |
| local file | read from disk, inlined | read from disk, inlined (still) | read from disk, painted |
| `data:` URI | kept as is | kept as is | painted |
| 403 / unreachable | exit 1, `failed to bundle … expected status 200 but got 403`, partial output with the link kept | success, link kept (never fetched) | success, placeholder painted (smaller file), no error |
| remote SVG with gradients outside `<defs>` (Chrome, Safari icons) | success, inlined | success, link kept | **exit 1**: `scene: shape "x" SVG asset: d2svgimport: …: element <linearGradient> must be a direct child of <defs>` |
| local SVG, same gradients | success, inlined | success, inlined | **exit 1**, same message |

What this establishes:
- Native D2 has more than one image behaviour, and which one you get depends on the output. SVG output either fetches and inlines remote images (the default) or leaves their link; PNG paints bytes through the same `imageasset` resolver and `d2svgimport` that d2web's scene builder uses.
- **d2web's present behaviour is the PNG/scene path minus the network and the file system.** Remote and unresolvable images give the placeholder without failing, as in native PNG. The rejection of Chrome and Safari icons is D2's own scene-builder rule, with the same message natively, so it is not a d2web deviation. It is a limit of the scene path that native SVG output does not have.
- Local files are always resolved natively and never exist in a browser; `data:` URIs behave identically everywhere.
- A failing remote image is a hard error in default SVG output (with a partial result) and a silent placeholder in PNG. A web runtime has to choose; native does not give one answer.
- This corrects two statements made earlier in the session: native SVG's default is to inline (not keep the link), and the Chrome-icon failure is not specific to d2web.

Not established here: native `.pdf`, `.pptx` and `.gif` outputs; TALA (no plugin installed), and any effect of the layout engine on images; behaviour behind a proxy or with a slow host; limits (the raster resolver sets byte, pixel and count limits in `d2cli/raster.go`, one-minute timeout).

### Image links before layout, and consumer-supplied bytes (ADR 0011 open items, 2 November 2026)

Probe: [research/images.go](../research/images.go), test `mise run test:research:images` ([test](../research/images.test.mjs)). No network: the "remote" links are fake (`https://i.test/…`) and answered from a map the test supplies. One run, Linux.

- **Native PDF, PPTX and GIF behave like PNG** (same cases as the table above, dagre): remote images are fetched and painted, a 403 or unresolvable host paints a placeholder and succeeds, and the gradient-outside-`<defs>` SVG fails with the same `d2svgimport` message. So native has two image behaviours, not more: the SVG writer (bundle on or off) and the scene exporters (PNG, PDF, PPTX, GIF), which all agree.
- **The D2 compiler lists image links before layout.** `d2compiler.Compile` returns the graph without laying it out; walking `Objects`, `Edges` and the nested `Layers`, `Scenarios` and `Steps` graphs found every link in a source that brings them in through imports (`...@lib`), `vars` (`${logo}`), `classes`, a glob (`*.icon`), a quoted string, a `shape: image`, an edge icon, layers, scenarios and steps: 33 entries over four boards, 10 distinct http(s) links, plus one `data:` URI. Scenarios and steps inherit the base board's objects, so a link repeats per board.
- **That list is the set the scene builder asks its resolver for**: the 10 links the builder requested through the resolver's HTTP client were exactly the 10 the preflight listed (a `data:` URI is never requested). A shape with `style.opacity: 0` that is not an image is skipped by the builder (`shapeAssetIsEmitted`), so the preflight can list a link the builder will not request, which is harmless.
- **Cost**: preflight 0.9 ms against 63 ms for the full layout and build natively (a small diagram, TALA, seed 1); in WASM 27 ms against 732 ms. The preflight returns D2's parse and compile errors without running layout.
- **Bytes the consumer supplies reach the scene builder without patching D2.** `imageasset.Resolver` is a concrete type, not an interface, but its `HTTPClient` is a public option. A transport that answers from a map made `pic.svg` a real vector asset in the scene (two real assets plus D2's shared `image:unavailable`, against one real asset plus the placeholder when nothing is supplied); links not in the map still paint the placeholder and the build succeeds.
- **The scene has no link-only asset kind.** `d2scene.Asset` is documented as "a closed set of fully resolved, network-free scene resources": `FontAsset`, `RasterAsset` and `VectorAsset`. Every unavailable image shares one placeholder id, so the scene cannot say which link an image was. A `link` mode therefore has to carry the link on d2web's own side (the association payload keyed by object id), not in D2's scene; patching D2's scene contract is the other route and ADR 0009 allows patches only where D2 leaves no public way.
- **Native and WASM agree** on the lists, the requested set and the asset ids (checked by hand: the Node/WASM test in this sandbox cannot start, because the Go toolchain here lives inside the repo's module cache where `package.json` makes Go's `wasm_exec_node.js` an ES module; the existing `options` test fails the same way here, so it is an environment quirk, not this probe). The probe binary was run through a CommonJS copy of the launcher and matched.

Not established: arrowhead icons and icons inside `sql_table` and `class` shapes beyond what `shapeAssetIsEmitted` implies; the limits and timeout defaults; behaviour on the final worker protocol (this is the library layer under it); what a consumer does about local binary files.
