# Spec 0008: large boards (cost, budgets and honest limits)

Status: **accepted with the recommended answers to questions 1-4** (user, 31 October 2026). Builds on [spec 0001](0001-compile-protocol.md) (worker, latest-wins, abort by respawn, budgets), [ADR 0003](../adr/0003-runtime-shape.md) and [ADR 0009](../adr/0009-natural-web-forms.md): d2web adds no layout policy or hidden fallback of its own.
Delivered: delivered as far as audited 4 November 2026 (budgets exist); measured timings not re-run. A spec is a short-lived brief: it must end `delivered` (or be marked not delivered); an agent that finds it otherwise tells the user. (Audited 4 November 2026.)

## 1. What is known (research probes, Chromium WASM, synthetic boards)

| Nodes | TALA | dagre | ELK |
| --- | --- | --- | --- |
| 25 | 0.5 s | 38 ms | 37 ms |
| 50 | 2.7 s | 45 ms (100 nodes) | 31 ms (100 nodes) |
| 100 | 18-24 s | 45 ms | 31 ms |
| 150 | 55-70 s | - | - |
| 500 | - | 569 ms | 1.4 s |
| 1000 | - | 2.0 s | 5.6 s |

Native TALA is 5-6x faster with the same growth. The wasm is single-threaded. The worker keeps the page responsive (275 timer ticks, longest gap 12 ms during a 50-node compile) and an abort by respawn works. dagre and ELK give different layouts from TALA. Corpus-shaped boards (real diagrams, not synthetic grids) were not measured. The current defaults are a `maxNodes` budget of 100 000 scene nodes (far above what TALA can lay out) and a 120 s silent timeout in the client.

## 2. Proposal

The product cannot make TALA faster, and choosing another engine for the user is a layout policy (ADR 0009 forbids policies of our own). So this spec makes the cost **visible, bounded and documented**, and leaves the choice to the consumer:
1. **Measured limits table** in the docs from real corpus boards, per engine and browser (the numbers above are synthetic), regenerated by a mise task.
2. **A layout-time budget.** `budgets.maxLayoutMillis` (default 60 000, consumer may raise or lower): the client terminates and respawns the worker when a compile exceeds it and rejects with `TimeoutError` carrying `code: 'budget'`, so a runaway board cannot hold a worker for the full 120 s silent timeout. (The existing abort path is reused; no new worker feature.)
3. **A cheap size estimate.** `countObjects(board.association)` returns the shape and connection counts of a compiled board (an aborted compile has no board, so a consumer measures a smaller or earlier version), so a consumer can decide to retry with `layout: 'dagre'` or `'elk'` itself. d2web does not retry on its own.
4. **No new transport.** Progress events are not offered because D2's layout engines report none.

Not in this spec: partial or incremental relayout, a faster TALA, parallel layout, engine switching on the user's behalf.

## 3. Test plan (proposed)

1. Unit: `maxLayoutMillis` is validated and defaulted; a compile past it rejects with `TimeoutError` and the worker is replaced (scripted worker, no browser).
2. Browser: a board known to take longer than a lowered budget aborts in about the budget, the next compile works, and the page stays responsive.
3. Measurement task (`mise run measure:layout`, not in `check`): compiles the corpus boards with each engine in Chromium and writes the limits table; numbers are checked in with the date, machine and browser.
4. Counts: a small board reports the right object and connection counts in the result.

## 4. Open questions for the user

1. **Default layout budget.** Recommended: 60 s. Alternatives: none (consumer sets one) or 30 s.
2. **Automatic engine fallback.** Recommended: no, for the reason above. Alternative: an opt-in `fallbackLayout` option that retries once with the named engine, still the consumer's explicit choice.
3. **Which boards to publish limits for.** Recommended: the repository's 147 corpus boards plus the synthetic ladder (25-1000 nodes).
4. **Whether TALA is the default engine in the demo and docs.** Recommended: yes, since it is D2's own default, with the limits table next to it.
